# Harness 通用验收契约

本文件是所有 flavor、任务 playbook 和 agent 的唯一通用验收规则。专项入口只写自己的实现步骤并引用这里；不要复制一套并行流程。Harness 自身命令见 [MAP.md](../../MAP.md)。

## 按风险决定验收角色

以下任一项出现时，完成实现者自检后，必须由原实现者之外的角色执行独立 QA：

- 新增功能、业务规则变化，或改变用户操作流程；
- 数据保存、删除、迁移或恢复；
- 登录、权限或会话变化（包括鉴权、角色授权、会话过期或恢复）；
- API/DTO/错误码等接口契约；
- 公共组件、共享包、基座或其他公共能力；
- 需要在运行环境判断的交互、端差异、状态切换或视觉回归；
- 已有回归争议、用户报告或历史失败。

仅改低影响文档、纯文案或不改变行为的样式时，实现者可自检，但仍要记录核对范围。风险判断以实际变更和任务目标为准，不以文件扩展名代替判断。

## 顺序与责任

按以下顺序执行，不要求并行：

1. 实现者完成最小改动、自检和必要的自动化/手工证据，记录目标、实现引用、命令、环境和未验证范围。
2. 独立 QA 必须由原实现者之外的角色执行，只依据已确认目标和可追溯证据判断，不替实现者猜业务语义；实现者自检不能算独立 QA，同一实现者再次自测也不能算独立 QA，逐项给出通过、失败或受阻。
3. QA 发现可复现问题时，交回原实现者修复；原 QA 只做增量复验并保留原失败证据。
4. 同一问题连续两轮修复仍失败，才升级主 Agent 或 Sol，并说明阻塞原因、已尝试的修复和下一项决策；普通 lint、类型、测试、CSS 偏差和接口映射问题由原实现者直接修复。

QA 不得因缺少环境、权限、账号、设备或业务决策而伪造通过。无法执行时标记 `blocked`，写明所需环境和复验入口；环境恢复后按原失败项增量复验。

命中独立 QA 条件但缺少验证环境时，记录“需要独立 QA，当前受阻”，不能把它降级为执行者自检通过；同时列出已完成检查、未覆盖场景和解除阻塞所需的信息。

## 证据与判定

每次验收至少保留：

- 目标编号/来源与用户确认状态；
- 改动文件、实现状态、提交或工作区标识；
- 与风险匹配的命令、测试、运行步骤或截图，以及实际环境/视口；
- 通过/失败/受阻/未验证结果和未覆盖范围。

技术结果与用户业务验收分开记录：技术检查通过不代表业务目标已被用户接受。只有任务明确要求或存在业务决策时才安排用户业务验收；它不是所有任务的默认阻塞项。

## 最小交付检查

- 根导航、模板和 playbook 的本地链接在 Harness 包内成立；复制到目标项目后，条件路径明确，不把不存在的业务资料伪装成有效入口。
- `missing / draft / active` 状态边界和 Hook/脚本协议保持不变；外部需求草稿不进入 `docs/specs/`。
- 自检、doctor、目标项目 fast/full profile 和必要的独立 QA 结果均如实记录；未执行的检查写明原因。
