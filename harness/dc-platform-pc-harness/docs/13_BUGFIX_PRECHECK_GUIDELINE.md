# Bug 修复前功能梳理规范

## 目的

修复 bug 前，必须先梳理当前位置已有功能和影响范围，避免只修复当前问题，却破坏原有可用功能、交互流程或数据逻辑。

本规范适用于所有业务页面、组件、接口联调、状态管理和公共能力的 bug 修复。

## 修复前必须先梳理

开始改代码前，先确认并记录以下内容：

- 当前位置包含哪些已有功能。
- 当前 bug 属于哪个功能、哪个流程、哪个状态下的问题。
- 该位置是否有新增、编辑、删除、查询、筛选、分页、导入、导出、审核、提交、撤回等关联操作。
- 当前页面或组件依赖哪些接口、路由参数、状态缓存、权限、字典、枚举和全局配置。
- 是否有其他页面、组件或应用复用当前逻辑。
- 是否存在空数据、异常数据、加载中、接口失败、权限不足、只读、禁用等边界状态。

如果无法确认已有功能，不能直接修改实现；应先补充阅读代码、运行页面或向需求/测试/相关开发确认。

## 修复方案要求

修复方案必须满足以下要求：

- 只收敛当前 bug 的根因，不扩大无关改动范围。
- 不删除、不绕过、不弱化原有业务判断，除非已确认该判断本身就是问题来源。
- 修改公共组件、公共方法、组合式函数、store、请求封装时，必须同步检查所有调用方。
- 修改表单、表格、筛选、分页、弹窗、详情、审核流等通用交互时，必须确认原有交互链路仍然成立。
- 对兼容旧数据、历史状态、权限差异的逻辑保持谨慎，不能只按当前测试数据判断。

## 修复后验证清单

提交前至少完成以下验证：

- 当前 bug 已在原复现场景下修复。
- 同位置原有主要功能仍可正常使用。
- 与当前 bug 相关的反向场景、边界场景已验证。
- 受影响的新增、编辑、删除、查询、筛选、分页、提交等链路没有回归。
- 控制台无新增明显报错。
- 如涉及接口参数、数据结构或状态流转，已确认请求和响应符合预期。

涉及高风险公共逻辑时，应补充自动化测试或明确记录人工验证范围。

## PR 或提交说明要求

涉及 bug 修复的 PR 或提交说明中，应包含以下信息：

- bug 根因。
- 修改范围。
- 修复前梳理到的当前位置已有功能。
- 已验证的原有功能和边界场景。
- 未验证项及原因，如果没有则写明无。

## 基本原则

修 bug 不是只让当前报错消失，而是在理解当前位置已有功能的前提下做最小必要修改。任何修复都不能以牺牲原有功能为代价。
